Sistema de Gestão de Eventos Institucionais

Trocar os formulários soltos do setor de Eventos por um único fluxo: quem precisa de um evento solicita, o administrador aprova ou rejeita com motivo, e o que é aprovado aparece sozinho na grade pública.

Folha A4 · hoje, 20h GitHub · 23/10, 18h45 Defesa · 5 min 70 funcionamento + 30 engenharia

1. Ideia geral
Web app com agenda pública em calendário (aprovados, mês atual + 2, período configurável), área do solicitante (rascunho → envio → acompanhamento) e área do admin (cadastros, aprovação com justificativa, relatórios CSV). Conflito de local e horário bloqueado na API e no banco.
2. Telas
Início/calendário · Login · Minhas solicitações · Nova solicitação · Aprovação · Cadastros · Relatórios
3. Tecnologias
React + TypeScript + Vite · Node + Fastify · PostgreSQL + Prisma · Zod · JWT + bcrypt · Docker · AWS EC2
4. Responsabilidades
A banco, regras e seed · B API e auth · C front público e solicitante · D front admin, README e deploy

Como resolvemos o problema

Uma agenda que é consequência das aprovações, não uma segunda planilha.

Uma solicitação, um estado

Todo pedido tem status explícito. Editar, enviar, cancelar e aprovar só existem nos estados em que são permitidos, e o servidor valida. Esconder o botão não basta.

Conflito impossível

Mesmo ambiente, mesmo dia e horários sobrepostos a um aprovado: a API bloqueia no envio e na aprovação, e uma exclusion constraint do Postgres garante isso até em corrida.

Publicação automática

A grade pública é uma consulta dos aprovados do mês atual e dos dois seguintes. Aprovou, apareceu; cancelou, sumiu.

Ciclo de vida da solicitação

Os cinco estados do caderno e quem pode agir em cada um.

O calendário mensal mostra só eventos aprovados. O período padrão é o que o caderno pede, mês atual + 2, navegado pelas abas e setas; nos limites do período as setas ficam desabilitadas.
  • Período configurável: a quantidade de meses é um parâmetro do sistema (configuracao.meses_agenda_publica, padrão 3), não um número fixo no código. O admin pode ampliar em Cadastros › Configurações. A API usa o mesmo valor e recusa meses fora do período, então ampliar não exige deploy.
  • Ao lado do calendário, a lista “Próximos eventos” segue em ordem cronológica e mostra todos os campos exigidos: data, nome, tema, horário, local, palestrante e realização. Ela cumpre o item 6.1 sem depender de clique.
  • Dois eventos no mesmo dia em locais diferentes são permitidos (28/10). A cor indica o tema.
  • No celular, os eventos do calendário viram pontos e a lista vira a leitura principal.

Stack

Afinidade da equipe (React, TypeScript, Postgres, Docker, AWS) e o que mais pontua: banco real, regras no servidor, código organizado.

Front-endReact 19 + TypeScript + ViteReact Router, TanStack Query, React Hook Form + Zod, Tailwind no tema Enturma (verde #00562b, azul #347bb7, Helvetica).
APINode 22 + Fastify + TypeScriptREST. Módulos auth, solicitações, cadastros e relatórios, cada um em rotas → serviço → repositório.
BancoPostgreSQL 16 + PrismaMigrations versionadas, seed fictício cobrindo todos os estados, conflito garantido com EXCLUDE USING gist.
ContratoPacote shared com schemas ZodRascunho (parcial) e envio (completo): a mesma regra no formulário e na API.
AutenticaçãoJWT em cookie httpOnly + bcryptPerfis SOLICITANTE e ADMIN verificados por middleware em cada rota.
QualidadeVitest + ESLint + PrettierTestes da regra de conflito e das transições de estado; README com credenciais de teste e uso de IA.
Infra e deployDocker Compose · AWS EC2 + CaddyUm docker compose up sobe postgres, api e web. Plano B: rodar local, que o caderno permite.

configuracaoparâmetros do sistema, ex.: meses_agenda_publica = 3
-- Dois eventos APROVADOS nunca ocupam o
-- mesmo ambiente em horários sobrepostos.
-- '[)' deixa 19h–20h e 20h–21h coexistirem.
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE solicitacao
  ADD CONSTRAINT sem_conflito_aprovado
  EXCLUDE USING gist (
    ambiente_id WITH =,
    tsrange(data + hora_inicio,
            data + hora_fim, '[)') WITH &&
  ) WHERE (status = 'APROVADO');

A API consulta os conflitos antes de enviar e de aprovar, para dizer qual evento conflita. A constraint segura o caso de dois admins aprovando ao mesmo tempo.
